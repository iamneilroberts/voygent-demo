Making an AI feature you can verify

An LLM is nondeterministic. The interface around it doesn't have to be — Voygent wraps the model in a deterministic, tested, auditable shell.

An experienced engineer trusts deterministic code: you read it, you test it, the same input gives the same output. An LLM breaks that contract. The same prompt yields different text, and the model can state things that aren't true. So the reasonable objection is "how do I verify any of this?"

The answer isn't to make the model deterministic. It's to make its job small, and make everything around it deterministic and testable. This is one worked example: Folio Board, a whole-trip review widget that renders inside the chat. Here's what's deterministic, what isn't, and where the line sits.

You don't make an LLM deterministic. You make the surface around it deterministic, and you shrink the model's job to something you can check.

What an MCP App is

MCP (Model Context Protocol) lets a server expose tools the model can call over a standard wire format. The host — claude.ai, Claude Desktop — runs the tools the model picks. An MCP App adds a UI: the server registers a ui:// resource (HTML for a sandboxed iframe), a tool result references it, and the host renders that widget inline. So instead of a wall of text, preview_folio_board returns an interactive trip review.

resource + versioned URI: src/mcp/folio-board-app/register.ts:77,136-158 · tool: src/mcp/tools/preview-folio-board.ts:56-63

One spec primitive does the heavy lifting below: _meta.ui.visibility marks a tool visible to the model, to the app, or both.

The core trick: keep the data out of the model

The naive design returns the full trip into the model's context. It's large, it re-bills every turn, and once it's in context the model can read it wrong or paraphrase it into something false. Folio Board does the opposite. The model-visible result carries a tiny reference only — { __voygentFolioBoardRef: { tripId, rev } }. The widget then calls an app-only tool, folio_board_data (visibility ["app"], invisible to the model), to fetch the full projection itself.

ref: preview-folio-board.ts:215-230 · app-only data tool: register.ts:174-226

Measured on staging: the model-visible payload dropped from 36,621 B / ~9,155 tokens to 531 B / ~132 tokens — a ~98.5% cut, flat regardless of trip size. The full board the widget renders is about 22,000 tokens, and it never enters the model's context. The ADR records the proof: after a fetch and a pick, Claude could not read a non-selected option's price and said the data "weren't passed back to me."

numbers: docs/research/2026-06-12-folio-board-app-staging-smoke-and-token-cost.md:12 · docs/adr/0012-...md:88-95

This is a verifiability argument, not only a cost one. The model can't misreport data it never received. The widget renders from the real record, deterministically; the hallucination-prone channel is bypassed for the data, and the model is left to route.

The model can't lie about data it never sees. The widget reads the record; the model just opens the drawer.

The interface renders from data, not from text

The widget renders from the trip projection in storage, not from anything the model wrote. Same record, same render. Around that core it uses the current MCP Apps features deliberately:

  • Compact by default. Every decision group, every day, the whole Included section start collapsed to one line; the advisor expands what they want. It's a pre-send review surface, not where picks are made. folio-board-widget.js:240-261
  • Host-native theming. The widget consumes the host's 36 standardized CSS variables and fonts so it matches claude.ai light and dark. applyHostStyleVariables / applyHostFonts — folio-board-widget.js:2038-2039
  • Fullscreen on request. app.requestDisplayMode(), with the button shown only when the host advertises support. folio-board-widget.js:1454-1460,1212
  • Calendar export. The .ics is built in-widget (RFC 5545) and handed to the host via app.downloadFile(), because the sandbox blocks direct downloads. The generator is pure, so it's unit-tested directly. ics.js · folio-board-widget.js:1465-1479
  • Images past the sandbox CSP. _meta.ui.csp.resourceDomains widens the iframe's default img-src so committed hero images load. register.ts:104-106,145,153

One efficiency detail worth keeping: claude.ai web caches ui:// resources by URI and won't refetch on reconnect, so a static URI meant shipped widget updates never reached connected clients. The fix hashes the bundled HTML into the URI, so a content change is a new URI. widgetVersionTag() — register.ts:63-77

The payoff: write-backs that read like deterministic code

When the advisor edits in the widget — picks an option, sets a commission, edits a note — it does not ask the model to mutate the trip. It calls app-only write tools with guarantees you'd recognize from any careful backend.

five app-only tools (visibility ["app"], tier pro): register.ts:81-89 · registered in server.ts:393-406
  1. Stable addressing, not array index. A durable editKey of decision:<decisionId>:<optionId> identifies a target by identity, so a reorder can't redirect a write. register.ts:506-543
  2. Exactly one match, or refuse. The resolver returns target_ambiguous unless exactly one option matches — malformed data never silently writes to the first match. register.ts:519-528
  3. Optimistic concurrency. The write carries a rev; a mismatch returns version_diverged with the current rev. No lost updates. register.ts:601-604, :696-700, :443-445
  4. Bounded validation. validateCommissionPatch checks only the keys present — amount in [0, 1e6], pct in [0, 100], explicit null means clear. src/lib/commission-core.ts:132-155
  5. Access control, defense in depth. canCurate() requires both an interactive host and an advisor projection, so a client-shaped payload can never surface an edit control. folio-board-widget.js:239

The model can propose an edit. It cannot bypass identity-addressing, ambiguity-refusal, version-guarding, range-validation, or the advisor gate. The mutation path has the same properties as code you'd write and test by hand. The nondeterministic part is "the advisor clicked this option." The rest is deterministic.

The AI proposes. The write path disposes — by identity, exactly once, version-guarded, range-checked, role-gated.

You can verify the tool surface too

list_my_tools enumerates every tool actually registered for the session, read from inside the server — the model cannot hallucinate the list. The catalog is locked per session, so what the agent can do is fixed and inspectable. You don't take the model's word for its own capabilities; you read them off the server.

src/mcp/tools/introspection.ts:54-55

Where the line sits

Nondeterministic, and that's fine: which tool the model calls, with which arguments, and the prose it writes around the widget. Deterministic and tested: the data fetch, the render, validation, persistence, concurrency, and access control, behind roughly 4,098 VERIFY unit tests at the time the commission tool merged. The pattern generalizes: shrink the probabilistic core to a routing decision, and make every shell around it deterministic and unit-tested. That's how an AI feature gets the verifiability of ordinary code.
